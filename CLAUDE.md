# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Vládoměr (vladomer.cz) tracks how the Czech government delivers its programme statement: 143 commitments, re-assessed every Friday by a language model, published as a static site. The site's only asset is being believable, so most of the design decisions below trade convenience for verifiability.

The UI, the prompts and most code comments are in Czech. Keep it that way.

## Commands

```bash
npm run dev            # http://localhost:5173
npm run build          # also generates /prehled/, /overview/, prompty.json and the JSON-LD
npm run evaluate       # the weekly run — COSTS MONEY, needs ANTHROPIC_API_KEY
npm run og             # redraw public/og.png (needs Chrome)
npm run instagram      # build the weekly post; --rezim verify|build|publish
npm run prispevek -- --zadani ig-posts/….json     # ad-hoc carousel
npm run reel -- --zadani ig-posts/….json          # ad-hoc reel (needs ffmpeg)
```

There is no test runner and no linter. Seven free offline checks stand in for them and should be run after touching what they cover:

```bash
node scripts/dev/test-korektura.js      # proofreading guard: forged corrections must be rejected
node scripts/dev/test-zabrany.js        # evidence bar for "fulfilled", against real past evidence
node scripts/dev/test-prechody.js       # transition gate, on fixtures from real oscillations
node scripts/dev/test-delta.js          # the delta scan's answer and chapter plan; an unread scan re-evaluates, never looks calm
node scripts/dev/test-odpoved.js        # reading the evaluation answer: one-item chapters, prose in front, truncation
node scripts/dev/test-sbirka.js         # Collection register: parsing, number checks, outage fallback (fixture of real e-Sbírka answers)
node scripts/dev/test-konzistence.js    # published data against itself and against the five metric sites
node scripts/dev/test-modely.js         # model-call layer: today's bodies unchanged, 5.x bodies, stream assembly, cost, fuse, refusal
node scripts/dev/test-faktcheck.js      # deterministic fact-check rules on real evidence (fake act numbers, wrong promulgation dates, cs/en)
node scripts/dev/test-psp.js            # Chamber open data: UNL/ZIP reading, bills of the current term, act → bill history (real excerpt)
node scripts/dev/test-rozhodnuti.js     # what a run may publish: held items, corrections without an event to the owner, audit and history, the PR's commands
node scripts/dev/test-report.js         # the owner's report from real records: every item to decide with its command, no e-mail address anywhere
node scripts/report.js --fixture        # build that report (HTML/PDF, pro-AI.md, PR text) into report/ — free, offline
npm run build && node scripts/kontrola-webu.js   # the built site against the data: headline, /prehled/, /overview/, JSON-LD (needs Chrome)
node scripts/faktcheck.js               # deterministic fact-check of the published data (free; network for e-Sbírka and source links)
ANTHROPIC_API_KEY=x CHAPTER_LIMIT=18 \
  node --import ./scripts/dev/dump-prompts.js scripts/evaluate.js   # prints every prompt, sends nothing
```

All seven run in CI on every push (`deploy.yml`, `dev-eval.yml`, and `parita.yml` on DEV2 — until 2026-10-20 only three of them actually did), and `test-konzistence.js` runs again on the weekly run's fresh data *before* it is committed: a failure there uploads the produced JSON as an artifact and stops the job, so the site keeps last week's data rather than publishing something that contradicts itself. It separates **CHYBA** (exit 1 — the site is inconsistent now) from **VAROVÁNÍ** (exit 0 — one data value away from being inconsistent); a warning is a finding, not noise. It imports its rules from `lib/dukaz.js`, `lib/korektura.js` and `src/data.js` rather than restating them, for the same reason `prepocet-degradaci.js` does.

`dump-prompts` is the tool for any change that could alter what the model receives: capture its output before and after and diff. An empty diff is the proof. It restores `public/*.json` (and removes a `naklady.json` the run created) on exit, so it cannot clobber live data. It reads e-Sbírka and the Chamber's open data for real (free, read-only), answers the model check `GET /v1/models` itself and answers in SSE when the request streams — between spec 002 and release B it did neither and failed on the first call.

**Parity with `main` (`scripts/dev/parita/`, spec 001).** `node scripts/dev/parita/porovnej-vetve.js` answers one question for a branch that rebuilds the process (DEV2): given the *same inputs*, does it send the model the same texts and reach the same published data as `origin/main`? It runs the real `scripts/evaluate.js` of both sides in temp copies — base via `git archive`, DEV2 from the working tree including uncommitted changes — with the base's `public/*.json` and `nastaveni.txt` on both, a frozen clock and no network: the `--import` loader `zmrazit.js` serves e-Sbírka from fixtures and model answers from `syntetika.js`, a deterministic simulator that builds answers from the published records and, keyed on a hash of the id, injects every path the program has — accepted, held, verified and rejected transitions, a non-existent act (demoted), a real act (date aligned, text given to the verifier), `<cite>`, a fixable dash for the proofreader, a one-item bare object, prose before the JSON, a truncated answer, an answer with no JSON, an unreadable scan, an invented news URL. It then compares every request body in order, the four output files, the protected files byte for byte (all prompts, whitelists, the guard libraries, `src/data.js`, `src/zmeny.js`), the corpus replays, and runs **main's** offline tests against DEV2's code. Three scenarios take about ten seconds and cost nothing; `parita.yml` runs it on every push to DEV2. The log is compared for information only — a new log line (a cost summary) is not a process change. Intentional differences go into `vyjimky.json`, each with a reason; an undeclared one fails. Seven deliberate sabotages (a word in two prompts, a guard threshold, the gate condition, audit order, the verifier's date, `max_tokens`) were each caught when the tool was written. Two things it cannot see by design: the model's own variance (measured against the golden set, spec 002) and anything outside the pipeline (the site's UI). The loader and simulator are shared by both sides, so changing them changes both — they measure pipeline code, not themselves. A guarded file differs even by a comment. Because `main` is not touched during the refactor, every intentional deviation is a patch listed under `zmeny` in `vyjimky.json` (applied to the base before anything is compared) — the first one, `01-minuly-od.patch`, gives the transition verifier the day the item entered its state (`stavOd`) instead of the day its record was last rewritten. A patch that no longer applies means `main` moved: merge `main` into DEV2 and regenerate it.

`prehraj-stary-doklad.js` does the same for the transition gate's old-evidence rule, over every transition in `audit.json`; its header lists its blind spots.

`prehraj-zabrany.js` is the same idea for the evidence bar: it replays `lib/dukaz.js` over every rating in `audit.json` — the full corpus of what the model has actually written, run after run — and prints which ones the bar would demote, with the verbatim evidence under each. Capture it before and after a rule change; the diff is that change's entire benefit and its entire cost. It is a tool, not a seventh check: it never fails, because a new demotion can be a correct catch as easily as a regression, and only a human reading the evidence can tell which. Note its one blind spot — `audit.json` records the status *after* degradation and has no `evidenceMissing`, so the corpus is the set of ratings that passed the bar at the time, which is exactly the set a tightened rule needs to be tried against.

The `/kontrola` skill (`.claude/skills/kontrola/`) drives a wider audit — data consistency, fact-check, UI, code, security — on top of those three. Its reports go to `kontroly/`, which is gitignored on purpose: a security finding in a public repo is a disclosure.

## What costs money

- **Push to `dev` touching `scripts/**`, `src/data.js` or `dev-eval.yml`** → a paid five-chapter evaluation (`.github/workflows/dev-eval.yml` path filter). Front-end work on `dev` is free.
- **Push to `main` never evaluates.** `deploy.yml` gates the evaluation step on `github.event_name != 'push'`, so merges only build and deploy. The model runs from the Friday cron or a manual dispatch. This also means `scripts/` can be edited for free on `main`.

Before running anything that calls the API, ask whether a dry-run tool answers the question instead.

## Architecture

Three separate things share one repository:

1. **The site** — React + Vite, `src/App.jsx` (one large file by choice). Fetches `public/*.json` at runtime; the browser never calls a model and never sees a key.
2. **The weekly pipeline** — `scripts/evaluate.js`, run by GitHub Actions on Fridays at 09:00 UTC. Writes `evaluations.json`, `history.json`, `news.json`, `audit.json` back into the repo, which triggers a deploy.
3. **Build-time generation** — plugins in `vite.config.js` emit the static listings at `/prehled/` and `/overview/`, `prompty.json`, and the JSON-LD injected into `index.html`. Anything containing current figures is generated, never committed by hand, because a hard-coded number is wrong within the week.

`scripts/lib/` holds what the pipeline and the build share: `nastaveni.js` (settings + strict templating), `prompty.js` (prompt assembly), `korektura.js` (proofreading), `prehled.js`, `seo.js`.

### Invariants worth knowing before editing

**The strict metric exists in five places** — `src/App.jsx` (`donePct`), `scripts/og-image.js`, `scripts/lib/seo.js`, `scripts/lib/prehled.js`, `scripts/instagram/post.js`. It is `fulfilled / rated`, with `unverifiable` excluded from the denominator; partial and in-progress are reported separately and never folded in. Change the rule in one place and the page, the share card, the structured data, the listing and the Instagram post will state different numbers for the same cabinet.

**The gauges are a stack, and a rounded cap overstates a segment.** The four arcs are cumulative from twelve o'clock, longest painted first, so the colours run into one another instead of meeting at a pinch — and therefore **no arc may use `opacity`**, or overlapping colours blend and stop matching the legend. `stroke-linecap="round"` adds half the stroke width beyond each end, which on the Instagram gauge is 3.4% of the circle per segment and on the site's `Ring` almost 4% — enough to draw 5.7% as 9.1%. Both gauges therefore shorten each arc by the stroke width and shift its offset by half, so the *painted* span equals the true share, and both fall back to butt caps for a segment shorter than the stroke, which cannot be rounded without inflating it. The geometry is deliberately duplicated in `src/App.jsx` (`Ring`) and `scripts/instagram/post.js` (`oblouk`) rather than shared across the src/scripts boundary; if you change one, change the other. `scripts/og-image.js` is exempt — its arcs are cumulative from a common origin, so only the outer cap is ever visible.

**`vite.config.js` `base: "./"` must stay.** It keeps the build working from both the domain and the github.io project path.

**`scripts/nastaveni/` is owner-editable plain text** — prompts, tunable numbers, source whitelists — deliberately outside `public/` so it is not published, and pinned to LF by `.gitattributes` because it is read at runtime. `scripts/nastaveni/NAVOD.md` documents it for a non-programmer; keep that promise.

**`render()` in `scripts/lib/nastaveni.js` is strict on purpose**: an unknown placeholder, an unused value, or any leftover `{{` all abort the run — including a `{{` written inside an HTML comment. That is what stops a broken template reaching the public site or a social profile.

**The weekly run is event-driven, not a fresh re-grade (since 2026-08).** Asking "what is the status?" 143 times a week re-rolled every judgment call — item 14.1 changed status five times in five runs with no event in the world; the headline swung a full point on noise. The pipeline is now: delta scan per chapter (`prompt-delta.md`, "what HAPPENED since <last run>?") → re-evaluate only items with a dated event → a deterministic transition gate (`lib/prechody.js`) → for transitions from or into `fulfilled`/`broken`, verification by a stronger model (`prompt-overeni-prechodu.md`, default answer NO) → a full audit of all items every `plny_audit_dni` days (stamped as `posledniPlnyAudit` in evaluations.json, only when complete). Items the run checked but did not re-write carry an `overeno` timestamp; both `src/App.jsx` and `scripts/lib/prehled.js` treat `overeno || updatedAt` as freshness. A held or rejected transition keeps the ENTIRE previous record — the new comment would argue for the state that was not accepted. Evaluation and proofreading run at `temperature: 0`; the gate has fixtures in `test-prechody.js`.

**The measurement that justifies all of it.** `dev-eval.yml` has a `stabilita` mode: two runs from identical inputs, restore in between, diff the statuses, commit nothing. On the pre-change code two full runs of the *same afternoon* agreed on only 133 of 143 items (93.0 %) and their headlines differed by 0.71 p. b. — one run had item 2.10 `fulfilled` and the other `partial`, and 10.2 came out `broken` in one and `in_progress` in the other, so the site's strongest accusation was a coin flip. With temperature 0, the gate and Sonnet verification the same pair scores 141/143 (98.6 %) with Δ headline 0.00; the two survivors move only between `not_started`/`declared`/`in_progress` and cannot touch the headline. Re-measure this way after any change to prompts, gate or model — a plausible-sounding improvement to the prompt can easily cost reproducibility, and nothing else will show it.

**A verifier without search checks reasoning, not truth.** On 2026-08-21 an item reached `fulfilled` on the evidence "Zákon č. 270/2026 Sb., vyhlášen 26. 5. 2026" — a law number and a promulgation date inferred from the fact that the chamber overrode the Senate veto that day, which cannot also be the day of promulgation. The verifier approved it: its rule asks for a law in the Collection, the text names one, and it had no way to look the number up. Hours earlier the same verifier had rejected the same transition correctly, so this is not a prompt weakness but a missing capability. Three things now stand against it, and all three are needed: the verifier searches (`vyhledavani_overeni`, and its prompt asks it to *find* the cited instrument and answer NO when it cannot); the whitelist carries the primary records (`psp.cz`, `senat.cz`, `e-sbirka.cz`) that were missing, without which the model could not confirm promulgation even in principle and inferred it from a ministry press release; and `lib/dukaz.js` demotes a `fulfilled` that claims promulgation while citing no official domain. Note that the guard before this one matched the *words* "Sb." and "vyhlášen" in the evidence text — exactly what a fabricating model writes. Wherever a check reads prose the model produced, ask what a confident fabrication looks like to it. Adding a domain to the whitelist carries its own risk: one site that blocks Anthropic's crawler fails the whole query, not just itself, which is why commercial law databases are deliberately excluded.

**"Cites an official domain" is not the same as "the source shows the law exists."** The rule above did not close the hole it was written for. In the very same run of 2026-08-21, item 10.4 reached `fulfilled` on "Zákon č. 233/2026 Sb., … podepsaný prezidentem Petrem Pavlem dne 17. srpna 2026" — a number that no cited source carries and no search corroborates, with `evidence_date` set to the signature — and the guard passed it because one source was `mpsv.gov.cz`, a press release about the *Chamber approving the bill*. Two separate mistakes, and fixing either alone makes things worse. `gov.cz` covers every ministry press page, so it can never evidence promulgation; but narrowing the domains while the trigger still matched any `\bSb\.` would have demoted "novela zákona č. 117/1995 Sb." — naming the *amended* act — and re-armed exactly the over-eagerness that already cost two `fulfilled` items in one week. The trigger is therefore two-pronged: a Collection number **no older than the evidence date** (the evidence claims that instrument was issued, rather than merely naming an old one), or the words "ve Sbírce" with no number at all; and the source must be on `PRAMENY_SBIRKY` — e-Sbírka and the two chambers, whose bill pages carry the number — with `gov.cz` deliberately absent. The year test is not the banned one: *that* rule demoted when the act's year **differed** from the evidence date and so punished amendments, while this one fires only when the number is as new as the claim, which is the opposite predicate and the opposite failure mode. Say so in the comment, or someone will revert it as "the forbidden year comparison". Replayed over all 32 `fulfilled` ratings ever published (`prehraj-zabrany.js`), the new rule catches 5 and the old caught 2, **with no overlap**: the two the old rule caught were an old regulation cited as context and an honest "novela č.... (k publikaci)", while three of the five new catches had their law number *change between runs* — 220+221/2025 became 334/2025 in three days, 16/2026 became 341/2017 in a week. An unstable number is the fabrication signature; a guard that reads only one week's prose cannot see it, which is why the corpus replay matters more than the fixtures. And note why the verifier cannot stand in here: `posudPrechod` returns `prijmout`/`stav-drzi` whenever the status is unchanged, so 10.4 went `fulfilled` → `fulfilled` with a rewritten law number and never reached the verifier at all. A check that only inspects transitions is blind to evidence rewritten underneath a stable status.

**The model writes `[2.3]` in prose, and that is a bracket too.** Reading the evaluation by slicing from the first `[` to the last `]` starts mid-sentence whenever the model prefaces its answer with a summary that references items in brackets — which it does often, and more so since the prompt gained the anti-fabrication paragraph. A dress rehearsal against production data lost seven chapters of eighteen to it, while every offline fixture still passed, because the fixtures had no prose in front. `lib/odpoved.js` now extracts *balanced* bracket spans (string- and escape-aware) and takes the first one that parses into records. The lesson generalises: a unit test written from what you imagine the model returns proves less than one line of a real transcript, so fixtures in `test-odpoved.js` are copied from actual runs.

**Two parsers read model output, and fixing one did not fix the other.** The balanced-bracket fix for the `[2.3]` prose went into `lib/odpoved.js` on 2026-08-26; `lib/delta.js` kept its own first-bracket slicing, and the next three weekly runs (28 Aug, 4 Sep, 11 Sep) each lost the scan of two or three chapters to `nevalidni-json` — chapter 4 in all three. All four readers of model output — evaluation, delta scan, verifier and news — now use the one `vyrezy()`, `scripts/` contains no first/last-bracket slicing any more, and an unreadable scan carries the first 300 characters of the answer into the log. When a fix concerns how model output is read, grep for every other place that reads model output.

**`overeno` is a claim that someone looked.** The site renders it as "prověřeno beze změny" and treats it as proof a chapter is fresh (`App.jsx`, `prehled.js`), which suppresses the stale-chapter notice. It used to be stamped on every item a run did not re-evaluate — including the items of a chapter whose scan could not be read, and items the model silently left out of its answer; on 2026-09-11 chapter 4 claimed a check nobody had made since 28 Aug. `planKapitoly()` in `lib/delta.js` now re-evaluates the whole chapter when its scan cannot be read (transitions judged as in a full audit, so no noise returns), and `prenesNeprehodnocene()` stamps only items a *read* scan covered. An item the model omitted stays exactly as it was, unstamped, and the log names it.

**A truncated answer is read to its last complete record, and the rest is asked for again.** In the dev run of 2026-09-11 chapter 6 asked for six items and got one: the answer hit `max_tokens`, its outer `[` never closed, and `odpoved.js` returned only the first complete object although the next one was complete too. It now collects every complete record, `evaluateChapter()` reports `stop_reason=max_tokens`, and the chapter loop asks for the missing items once more as a separate, smaller batch — a smaller request fits, and unlike a retry at temperature 0 it gets a different answer. The follow-up is best effort: if it fails, the items stay as they were and the log names them, but the chapter does not fail, which would throw away what the first batch evaluated correctly. That last rule came from a dry run, not from reasoning: the first version failed the whole chapter when the follow-up returned an empty list.

**A transition resting on evidence older than the current state is not an event.** The gate (`lib/prechody.js`) computes `stavOd`, the day the item entered its current state, from the history snapshots taken before the run, and compares it with the proposal's `evidenceDate`. In a delta run an older date holds the transition (`doklad-starsi-nez-stav`); in a full audit it is only listed "ke kontrole", because a full audit exists to catch missed older events. Code-guard demotions and proposals without an evidence date are untouched, and `drzet_stary_doklad = 0` switches the hold off. The verifier had the same rule in its prompt and applied it inconsistently within single runs — on 2026-09-18 it rejected 15.4 and passed 17.3 and 10.2, on 2026-09-25 it rejected 9.7 and passed 2.11. Replayed over the delta era, the rule holds exactly those three plus 15.5 (evidence citing "the Fiala government in February 2026") and 12.6, and blocks none of the correct transitions. When the latest snapshot does not carry the current status, `stavOd` is null and the rule stays out, since a wrong date could hold a real event.

**The model cannot see the Collection of Laws, so the program reads it for it.** e-Sbírka is a JS application that search engines barely index, and zakonyprolidi.cz blocks Anthropic's crawler outright, so law numbers in evidence were guesses: item 10.4 cycled through five numbers in six weeks without once hitting the real one (152/2026), and more often the model cited a *real* act on another topic (360/2025 for the parental allowance, a NÚKIB portal decree for the drug-policy amendment). `lib/sbirka.js` loads the register once per run from e-Sbírka's open JSON API (`POST /sbr-cache/chronologicke-rejstriky/dokumenty-sbirky-po-mesicich` with `{"rok": N}` returns a whole year; no auth). The evaluation prompt gets the ~180 laws, government decrees and ministerial decrees issued since the cabinet took office (`{{REJSTRIK_SBIRKY}}`, ~9k tokens per chapter); every cited number in a coverable year is checked, and a number the Collection does not have demotes `fulfilled` (`neexistujici-predpis`). For a `fulfilled` resting on verified acts the promulgation date is replaced by the official one, the newest cited act's e-Sbírka page joins the sources, and — when exactly one verified act is cited — the date right after "vyhlášen" in the evidence text is aligned too, so the site never shows a corrected date beside an uncorrected claim. All five `fulfilled` ratings in the audit trail that cited a real number carried a wrong date. Whether the act actually concerns the promise is *not* something code can tell; the transition verifier gets each act's official title (`{{PREDPISY}}`) for that, and for a transition into `fulfilled` also the beginning of the act's text (`nactiZneni`, the `/fragmenty` endpoint, ~6000 characters). The title alone was not enough: in the dev test of 2026-10-15 item 1.3 went `fulfilled` on Act 91/2026 "amending the Building Act", which only moves a deadline from 2026 to 2027, while the other run's verifier rejected the genuine 90/2026 claiming it was not yet published — hence also the template rule that e-Sbírka outranks the verifier's own search. A freshly published act has no structured text for up to 30 days (only a header and a notice); that is detected by fragment type and told to the verifier as "zatím nezpracované". Rejected transitions are logged with the proposal's evidence, so a run check can tell a bad claim from a good claim rejected badly. A verified number replaces the `PRAMENY_SBIRKY` source requirement (the register is the official record); without the register — switched off by `rejstrik_sbirky = 0` or e-Sbírka down — the run behaves exactly as before, the prompt says the list is unavailable and the log says why. `dump-prompts.js` fetches the register for real (free, read-only), and the build's prompt example uses the test fixture, labelled as shortened.

**`previousStatus` is the last transition, not this week's.** Under the delta pipeline an item without an event keeps its whole previous record, `previousStatus` included, so its last real transition used to be reported as fresh forever: item 12.6 changed on 28 Aug and was still listed under "Změny od minulého týdne" on the site and as a change of the week in the Instagram posts of 4, 11 and 18 Sep. `src/zmeny.js` (`zmenaPoslednihoBehu`) is the single rule for the site's change panel, the trend arrows and the transition in an item's detail, and for `scripts/instagram/post.js`: a transition counts only if the last run wrote it, i.e. `updatedAt` lies within 12 hours before `lastUpdated`. A held transition, a carried-forward item and a manual correction that restores the previous record all keep the old `updatedAt`, so none of them shows up.

**A late scheduled run must not repeat the day.** GitHub fired the Friday cron at 20:40 on 2026-08-28, after the evaluation had already been run by hand, and the second run rewrote that day's audit rows — the append-only check only protects earlier days. `deploy.yml` now skips evaluation, share image and commit on a `schedule` event when `evaluations.json` is already from today; a manual dispatch always runs.

**A one-item chapter is a different shape of answer.** In delta mode a chapter often has a single item to re-evaluate, and the model then wraps the answer differently — as a bare object rather than `{"items":[…]}`. Slicing on the first `[` picks up its `sources` array instead, so no evaluation is found and the chapter fails; in the first delta pair *all four* one-item chapters failed and no chapter with more items did. A full run never showed it, because there every chapter has at least four items. `lib/odpoved.js` accepts every shape that still carries an evaluation (bare object, id→record map, differently named envelope) and, when it truly cannot read one, puts the first 300 characters of the answer into the error — a character position in a response nobody kept is not a diagnosis. Note the interaction with `temperature: 0`: the same input now yields the same answer, so `withBackoff` retrying a malformed response produces four identical failures. Tolerant reading replaced retrying, not the other way round.

**An answer with no JSON in it is asked for once more, in the same conversation.** On 2026-10-16 chapter 1 (one item, 1.1) came back as a Markdown analysis — "Vyhledám… Na základě vyhledaných informací nyní mohu posoudit… Analýza: …" — with no evaluation anywhere in it, and the whole chapter failed, which also cost the week its history snapshot. Tolerant reading cannot help when there is nothing to read, and a retry at temperature 0 repeats the same answer. `evaluateChapter()` therefore sends one follow-up turn (`prompt-doptani.md`) carrying the model's own answer and its search results back, so the citations still validate against `realMap`; on `stop_reason=pause_turn` it only lets the turn finish, as the API prescribes. Each unreadable answer is saved whole to `necitelne-odpovedi/` (gitignored) and `deploy.yml` attaches it as an artifact, because the 300 characters in the log did not show *why* — whether the JSON was missing, malformed, or cut off. The follow-up shows up in `dump-prompts` only in a full run, where the stub's `[]` cannot be read.

**A delta scan that cannot be read looks exactly like a quiet week.** Both produce no events, so nothing is re-evaluated, everything carries forward and a stability measurement scores it as flawless. `lib/delta.js` therefore never throws and never returns bare emptiness: every dropped event is counted by reason and the run log names chapters whose answer could not be read. The subtle case is one event returned as a bare object — slicing on the first bracket then extracts its `zdroje` array, finds no events among a list of strings, and reports calm. Note also that the scan's window is the previous run's `lastUpdated`, which after a same-day correction run is *today*; `OD_DATA` (env, or the `od_data` workflow input) overrides it, and without that a delta pair cannot be measured at all.

**A chapter that is too big silently truncates its own answer.** The reply grows with both the item count and the length of the comments; past `max_tokens` the JSON is cut mid-object and surfaces as `Expected ',' or '}'`, which looks like a model failure but is a budget failure — retrying cannot help, because the ceiling is the same every time. Chapter 2 (15 items) passed for four runs and then started failing on 2026-08-21. `evaluate.js` therefore splits any chapter over `MAX_BODU_DAVKA` items into even batches; a chapter counts as failed if **any** of its batches fails, so a chapter is never half fresh and half a week old. Splitting changes the item list in the prompt and nothing else — prove it with `dump-prompts` before and after.

**A failed chapter keeps its previous ratings** (the merge never overwrites), so the site would otherwise claim a freshness it does not have for those items. Both `src/App.jsx` and `scripts/lib/prehled.js` compute the stale chapters the same way — no item in the chapter carries the run's date — and say so, in the header and in the listing. Change one, change the other.

**Never ask the model for something the program already knows.** `change_cs` used to be free prose that included the status transition and the date of the previous assessment — both facts the code holds exactly. The model got them wrong constantly: a third of items every week claimed "první hodnocení" although they had been assessed before, and item 14.1 published "nyní splněno" under a "částečně splněno" badge, dated six days into the future. The prompt now asks only what happened *in the world*; `src/App.jsx` renders the transition itself from `previousStatus` → `status`. An empty `change` is therefore legal and `test-konzistence.js` allows it (an empty `comment` is still an error) — when a sentence turns out to be untrue it is deleted, never rewritten, because inventing what happened would publish an unverified claim.

**The fact-check starts with what the program knows (`scripts/faktcheck.js`, spec 004, layer D).** Before any model is asked whether a published sentence is true, the program checks what it can decide exactly, for free: every act number in evidence, comment and change against the e-Sbírka register (loaded for every cited year, not only since the cabinet took office), the promulgation date written after „vyhlášen“, the evidence date against the run date and the cabinet's start, Czech against English (dates, act numbers, percentages), whether each source link is alive and not redirected to a front page, a comment that opens by claiming a status the item does not have, and the result of `test-konzistence.js`. It reuses `overZnacky` and `opravDatumVyhlaseni` from `lib/sbirka.js` — the same functions the pipeline writes by — and saves the text of every source it could read, so the model layer later reads sources instead of searching for them. Severity matters: CHYBA is provably false against a primary record (and holds the item when the claim carries its status); VAROVÁNÍ may be fine and goes to the model and the owner. The rules were calibrated on the data of 2026-10-20, where a future date in a comment was nearly always an effective date („od 1. 1. 2027“), „8. červen“ is a legitimate nominative, and „devět procent“ is spelled out — none of which is an error. The first run found two real errors the golden-set review had missed: 1.2 and 15.4 present acts of the previous cabinet (236/2025 and 176/2025, promulgated in July and June 2025) as promulgated on 31 Dec 2025.

**The model fact-check cannot quote what the program already knows, nor what did not happen.** The first paid run of layer M (20 Oct 2026, round 1 on the 46 golden and control items, 2.30 $) flagged all 19 items the site gets wrong — and held 18 of the 27 it gets right, mostly on claims marked unverifiable. Two kinds were not the site's fault. An act number and promulgation date the program had verified in e-Sbírka had no source text to quote from (e-Sbírka pages are a JavaScript app; the downloaded text is empty), so `zdrojeSbirky()` in `lib/faktcheck/modelova.js` now turns each verified act into a citable source built from the register, listed first in the prompt and in the texts quotes are checked against. And a claim that something has *not* happened ("no bill has been submitted") cannot be quoted at all; the model now marks it `absence`, and an item whose status does not change is not held for an unverified absence — **only when the model, from the facts it did verify, reaches the same status as the site, and never at `not_started`**, where "nothing happened" is the whole reason for the status. The owner chose the plain rule; replayed over the measurement's answers it let 15.7 through (`not_started` on "the government took no step", while the bill sits in the legislative outlook — truth `declared`), which is the understating direction, so the exception went in; the second paid run (21 Oct) let 16.3 through the other way (`declared` on "the government has not commented", which contradicts the status — truth `not_started`), hence the condition that the model's own status must match. The same run also let through 8.7, whose deciding fact (the September budget proposal) is newer than any source the site cites — the fact-check checks the site against its sources and does not discover later events unless it searches, which is the monthly full audit's job — and 13.5, a reading of a promise's scope the owner rated low-to-medium confidence. The chain measurement (evaluation, fact-check and decision on the 46 items, 21 Oct, 17.71 $) let through 3.2, 8.7 and 13.5 — all readings of the rules, not invented facts — and led to three changes: the fact-check now gets each promise with its chapter and section (`slibySKontextem`; 3.2's "housing allowance" belongs to the security forces' pay, and without that the model accepted the social benefit M10 names as the counter-example); M3 now says that leaving a promise with a fixed date out of the draft budget for the year it was due to start is `broken`, even with a promised later attempt (8.7); and M7 counts a step covering only part of what a promise targets as `in_progress`, so the owner changed 13.5's truth to `in_progress`. Rules written from control-set items make those items no longer independent tests of them; the set says so. So zero let-through against the owner's truth cannot rest on the fact-check alone; it has to be measured on the chain of evaluation and fact-check together. A transition still needs every status-bearing claim verified, absence included. Holds of correct items are not all noise: in the same run the fact-check found 15.1 claiming a law awaits the President's signature after he signed it, a wrong date in 10.1, a "government-approved" bill in 12.7 that was an MPs' bill, an unsupported agreement in 6.8 and an unrelated decree cited in 3.2 — real errors under a correct status, which the golden-set score cannot see because it scores status only. Absence claims belong to primary records the program can read, which is what the Chamber's open data is for.

**The Chamber publishes every bill and its whole history; the program reads it like e-Sbírka (`lib/psp.js`, spec 006).** `tisky.zip` from psp.cz (UNL tables: one record per line, `|` between fields, a backslash escaping the next character including a newline, windows-1250, a full snapshot every day; column order documented at hp.sqw?k=1303) is unzipped with `node:zlib` — no dependency — once per fact-check run. The current term is the `id_org_obd` of the most recently submitted bill, ignoring the typo dates in the data (one bill is dated 3021). Each act an item cites is linked through `hist.zaver_sb_cislo` to the bill it came from, and layer M gets that bill's whole history as a citable source; items that are not `fulfilled` also get the complete list of the term's bills (171 on 21 Oct 2026, about 20 000 characters, never truncated — a truncated list would make its own completeness sentence false), against which "no bill has been submitted" can be confirmed or refuted instead of left unverified. That is model judgement over a complete official list, not a quote, and the docs say so. The first reading already corrected the picture: 90/2026 Sb. (item 2.10) came from an MPs' bill, not a government one. `zaver_sb_cislo` is only an act number on the step that closed the bill: on 21 Oct the column held 7 on the "change of the amendment deadline" steps of bills 189 and 198, and the fact-check's source text for item 10.4 read "promulgated as 7/2026 Sb." until `modelTisku` took the number only from a step with a promulgation date or the state KONEC. Prompts roughly doubled (18 750 → 36 900 characters on average), about +2.5 $ a month. When the Chamber is down the fact-check runs without it and says so. Since release B the evaluator gets the same list (`{{TISKY_PSP}}`, about 24 000 characters, with the Collection number and promulgation date of every bill that became law, because the state KONEC alone also covers a rejected bill); without the Chamber the prompt says the list is unavailable and the run goes on.

**What the owner decided, the program holds; how to judge, the prompt says.** Two sets of items whose real state the owner confirmed from primary records exist on DEV2: the golden set (`scripts/dev/fixtury/zlata-sada.json`, 22 items, used to choose the model) and the control set (`kontrolni-sada.json`, 24 items, on which no rule was written — the honest test for prompt changes). Score any `evaluations.json` against either with `zlata-sada-skore.js`. On 2026-10-20 the published site matched 16/22 and 11/24. The fact-check is scored against the same 46 items with `faktcheck-skore.js` (paid run: `rezim: faktcheck` in `mereni.json`, on the data committed to DEV2, which is what the sets were checked against): every item where the site differs from the truth must come out flagged — by a layer-D finding that carries the status, or by layer M not passing it clean — and the one number that must be zero is the items let through. Items flagged although the site is right are the owner's extra work, and the layer-M proposal is scored separately, because an item can be held rightly with a wrong proposal. The analysis of Sonnet 5.5's answers showed that in four of five errors the model found the same facts as the owner and classified them by different rules — rules (M1–M10, in the sets' `metodika`) that exist only in the owner's head and the sets, not in the prompt; one of them (M1: an act of the previous cabinet effective under this one is `partial`) even contradicts the prompt while matching `lib/dukaz.js`. Release B (spec 007, parity patch `03-vydani-b.patch`) put them there: the evaluator and both verifiers read `metodika.md` through `nactiMetodiku()` in `lib/prompty.js` — the same function the fact-check uses, so the four roles cannot judge by different rules — and the evaluation prompt's own status definitions, which contradicted M1 and gave a minister's statement as an example of `broken` against M3, were replaced by it. Every item line carries the section of the programme statement it comes from (`(oddíl „…“)`; the verifiers get chapter and section): 3.2 „Příspěvek na bydlení až 6 000 Kč“ belongs to the police pay section, and without it the evaluator and the fact-check both credited the social superbenefit to it, the very M10 example. Measured in the chain on 21 Oct (20.20 $), it did not move the evaluator's accuracy beyond run-to-run noise — its raw proposals matched the truth on 33 of 46 items against 32 and 33 before — while the evaluation cost rose by 38 %, because with web search the prompt is re-read in every search round, so ~30 000 extra characters cost five times what one read would. Run-to-run variance on these sets is two or three items, so one run cannot show a gain smaller than that; score the rehearsal's 46 items too before deciding. What does *not* belong in a prompt is a decision about one item that does not depend on events: unmeasurability is a property of a promise's wording, so `scripts/nastaveni/nemeritelne.txt` lists the items the owner ruled unmeasurable and `evaluate.js` sets `unverifiable` for them on every evaluation (declared parity patch `02-nemeritelne.patch`); since release B the prompt no longer asks at all, and an item off the list is never unmeasurable whatever the model writes. The decision also applies to a record the gate holds (`04-nemeritelne-pri-drzeni.patch`) and layer R does not treat it as a transition (`nemeritelne` in `rozhodnuti.js`): leaving `broken` needs a dated event, so the gate otherwise kept 5.4 measurable every month. Forcing statuses this way would be wrong — the world moves — so the list holds only time-invariant decisions. The deterministic fact-check flags an item on the list that the site still shows as measurable, a `fulfilled` whose own comment says „Ne, ale…“, and — read from `audit.json` — an item whose cited act numbers changed three or more times while its status did not (15.4 cycled 250 → 296 → 404 → 128/2026 → 176/2025, each „vyhlášen 31. prosince 2025“): the fabrication signature a check that inspects only transitions cannot see.

**What reaches the site is decided in one place (`lib/faktcheck/rozhodnuti.js`, layer R; `scripts/rozhodni.js` runs it after the fact-check).** A run is always published, and an item the fact-check did not confirm keeps its last confirmed record. A record the run rewrote is held — the whole previous record goes back — on any problem that carries the status: a layer-D CHYBA, a refuted or unverifiable claim, a status the owner's rules contradict, or no layer-M result at all. A transition must also rest on a claim layer M confirmed, and one resting on the same evidence text as before is not an event but a correction, which goes to the owner: in the measurement of 20 Oct 2026 Sonnet 5.5 moved 10.2 `in_progress` → `declared`, the verifier passed it and the golden set agrees, but nothing happened in the world. A record the run did not change keeps its *old* `overeno` when the fact-check does not confirm it, because a new stamp would publish "checked, no change" about something the check disputes. FR-009 is the reason the layer exists apart from the gate: 7.2 shows `broken` for a promise that was never broken, the correction has no event, so the gate holds it forever — when the fact-check disputes the current status, the held proposal goes to the owner with the gate's reason. `evaluate.js` writes held and rejected proposals to the file named by `NAVRHY_BEHU` and only then, so its outputs and parity are unchanged. `faktcheck_kalibrace = 1` sends every transition to the owner during the first two monthly runs. Only items with something to decide reach the owner: a transition, a dispute over the status, a refuted claim, a layer-D error. A record whose status did not change and whose only problem is an unverified claim in the new wording keeps its previous record without a new stamp and is merely counted (`souhrn.ponechano`, owner's decision of 22 Oct 2026) — in the rehearsal of 21 Oct that was 64 of 107 items, and a monthly full audit rewrites nearly every comment, so without the rule the owner would read 60–100 text diffs a month with nothing to decide. Round 2 of the fact-check therefore takes transitions first, then items whose round-1 result disputes the status, then `fulfilled`/`broken`. Today's audit row of an item that did not go out gets `zadrzeno` and the reasons — it is this run's row, not yet published, so append-only still holds — and today's history snapshot carries the status the site actually shows.

**One module knows how each model is called (`scripts/lib/modely.js`, spec 002).** Every API call — four in `evaluate.js`, one in `lib/korektura.js` — goes through `teloPozadavku()` + `zavolejApi()`. The profile is chosen from the model id. Today's models (Haiku 4.5, Sonnet/Opus 4.6, and an unknown id like the tests' `"x"`) get *exactly* the body they got before — parity proves it, including a pass against `main` without the new files. Models that think (Opus 4.7+, the 5.x family, Fable) get no `temperature`, which they reject with a 400, adaptive thinking with `effort_hodnoceni` / `effort_kontroly` from the settings, a reply limit large enough for thinking (`limitPremysleni`), `stream: true`, `web_search_20260209` where supported, and the server-side `fallbacks: "default"` where the API offers it. The stream is assembled into the non-stream shape block by block, thinking signatures included, so the follow-up in the same conversation can send them back unchanged — preserved thinking rejects edited blocks. The module also prices every call (table dated 2026-10-06; an unknown model is priced as the dearest tier), records the model that actually answered (`model_skutecny` in the audit row, only when it differs), and keeps the fuse `pojistka_ceny_usd`: once spent, no further request leaves, and the run exits with code 3 so nothing is committed. A refusal and the fuse deliberately produce messages `withBackoff` will not retry. So does an account error — credit exhausted (HTTP 400 "credit balance is too low") or the key refused (401/403): it concerns every later call, so `zavolejApi` sends nothing more and both `evaluate.js` and `faktcheck.js` exit with code 3, which fails the monthly run before anything is published. Exhausted credit is first waited out (1, 3 and 10 minutes, `CEKANI_NA_KREDIT`): the owner's account reloads itself once the balance drops below a threshold, and the batch's charge of 9.66 $ landing at once is what emptied it a minute before round 2 started — stopping at once would throw away a paid run over a dip. In the rehearsal of 21 Oct 2026 the credit ran out during round 2; the 95 failures were recorded as per-item errors, the run finished green and the e-mail offered 107 items to decide. `overModely()` checks the configured ids against `GET /v1/models` before anything is paid. The run's cost goes to the log and to `public/naklady.json`. Losing `temperature: 0` with the 5.x models is accepted: reproducibility was a means against status flapping, which the gate, the verifier and (later) the fact-check now carry. Measure a model on the golden set (`node scripts/dev/zlata-sada-skore.js`; paid runs via `dev2-eval.yml`) before switching to it. That workflow is triggered by a change to `scripts/dev/mereni.json` on DEV2, not by a button — GitHub offers `workflow_dispatch` only for workflows on the default branch, and `main` is not touched — and it pays for nothing unless the file's `schvaleno` names who approved the run and when, so every paid measurement is on record in git. Empty `schvaleno` again after the run.

**Error message strings are load-bearing.** `withBackoff` decides whether to retry by matching `/API (429|5\d\d)/`, `/JSON/` or the `[opakovat]` marker in the message text.

**Dead ends, already paid for:** structured outputs (`output_config.format`) and assistant prefill each silently suppress the `web_search` tool, leaving the model with no sources. JSON stays prompt-enforced. Raising `vyhledavani_zpravy` makes the headline step worse, not better — search rounds consume the same output budget the JSON needs.

**Guards belong in code, not prompts.** The model has repeatedly produced true-but-irrelevant facts that instructions alone did not stop: `evaluate.js` therefore drops invented URLs, downgrades a `fulfilled` claim with no citation, and refuses evidence dated before the cabinet took office. The rule itself lives in `scripts/lib/dukaz.js`, not in `evaluate.js`, because already-published data has to be recomputable by exactly the same rule (`scripts/dev/prepocet-degradaci.js`); two copies would drift.

**A guard that is too eager is as damaging as no guard.** The date check used to compare the year inside a cited act number against the evidence date, which quietly demoted the single most common way a promise gets delivered here — an amendment to an older act ("novela zákona č. 117/1995 Sb., schválená 8. 7. 2026"). It cost two `fulfilled` items in one week and made the site *understate* delivery, which for a watchdog is the worst direction to be wrong in. Comparing years cannot work: this cabinet took office on 15 December, so "2025" is ambiguous. The rule now asks whether the *only* thing tying the claim to the term is the day an older rule took effect. Any change here needs `test-zabrany.js`, whose fixtures are verbatim evidence strings from real runs.

**`audit.json` is append-only and the site says so in three places** (methodology, FAQ, "how do I know you're not making this up"). Corrections are appended as new entries carrying an `oprava` field — never written over the original row. Breaking that promise to fix a number would cost more than the number is worth.

It was cut from `main`, not from `dev`, which had fallen eight commits behind. Until it merges, `main` keeps running weekly and **the refactor does not touch `main`** (owner's decision, 2026-10-20): DEV2 takes `main`'s data and any fixes the owner makes there, never the other way round. An intentional change to what the model reads or how the program decides is recorded on DEV2 as a patch in `scripts/dev/parita/zmeny/` with its reason; `parita.yml` applies those patches to `main` and proves DEV2 equals `main` plus them, nothing else. Pushes to DEV2 cost nothing — no workflow evaluates on them.

**The monthly run lives in one reusable workflow, `mesicni-beh.yml`** (DEV2; it replaces the Friday evaluation when DEV2 merges). `deploy.yml` calls it on the 1st of the month at 05:15 UTC and on a manual dispatch (`rezim_behu: delta` is the extraordinary run), and builds and deploys only after it succeeds; `dev2-eval.yml` calls the *same* workflow as a dress rehearsal (`rezim: generalka` in `mereni.json`, `zkouska: true`), so a rehearsal tests exactly what will run: the run is committed to a throwaway branch `zkouska/RRRR-MM` instead of `main`, the PR `beh/RRRR-MM-zkouska` targets that branch, the e-mail says `[ZKOUŠKA]` and its decision links work, "Publish" merges into the throwaway branch and only builds and checks the site as an artifact, and the Instagram post is built from the run's data as an artifact — nothing reaches `main`, vladomer.cz or Instagram. The cost cap covers the whole run — the fact-check starts from what the evaluation already spent (`public/naklady.json`), otherwise each process could spend the full cap — and the fact-check's batch goes in parts, because a batch once sent cannot be stopped. The PR branch is always *recomposed* (`scripts/navrhy.js`, `lib/navrhy.js`) from the run's commit plus the list of accepted items in `navrhy/RRRR-MM.json`, so no command overwrites another; acceptance is a new audit row with `oprava`, which the audit's order and duplicate rules already exempt. The e-mail and the PDF carry, for every item, an "Accept" and a "Keep" link and a final "Publish" link (`odkazRozhodnuti` in `lib/navrhy.js`). GitHub cannot pre-fill a PR comment, but it can pre-fill a new file on a branch, so each link opens the editor with `rozhodnuti/10.2-prijmout.txt` containing `/prijmout 10.2` on the PR branch and the owner only commits it. That push triggers `rozhodnuti-vetev.yml`, which runs from the branch itself — so it works on a rehearsal before DEV2 merges, which the first design (a pre-filled issue) could not: GitHub hands `issues` and `issue_comment` events only to workflows on the default branch. It checks that the owner pushed, applies every file in the order the commits added it (`navrhy.js soubory`; "accept" then "keep" means keep), deletes the files, recomposes the branch, answers in the PR and, on `/zverejnit`, merges: into `main` followed by a `deploy.yml` dispatch with `jen_nasadit` (a push made with the workflow token triggers no workflow, and the input keeps the dispatch from evaluating again), or for a rehearsal into `zkouska/RRRR-MM` with the site only built. A file without a valid command (an empty "duvod:") is reported, not applied. The file contents go through the same strict regex as comments and are never executed. PR comments (`/prijmout`, `/podrzet`, `/zverejnit`) remain as the fallback in `rozhodnuti.yml`, read only from the repository owner, through an env var, with the scripts run from the default branch and the PR branch checked out beside them as data — so comments work only after the merge, and only on the real PR. Creating the PR needs the repository setting that lets Actions create pull requests; without it the e-mail links to the branch comparison instead. `pripominka.yml` reminds the owner every three days while a `beh/*` PR is open.

**Secrets.** Instagram and Anthropic keys live only in GitHub Actions secrets. The one key that must exist locally is `ELEVENLABS_API_KEY`, because reels are built on the owner's machine — it belongs in `.env.local`, covered by `*.local` in `.gitignore`. Vite reads that file too, but only exposes `VITE_`-prefixed vars, so the key does not reach the bundle (verified by grepping `dist/`). A pre-commit hook in `scripts/dev/hooks/` refuses to commit anything key-shaped; enable it in a fresh clone with `git config core.hooksPath scripts/dev/hooks`. The hook reports line numbers only and never echoes the matching line — hook output ends up in CI logs and session transcripts, where printing the secret would just move the leak.

`.env` **is committed** and holds `VITE_MENU_*` feature flags — never secrets. It differs per branch by design (dev: everything on; main: only what is public), so a conflict when merging `dev → main` is expected: **keep main's version**, and keep main's `public/*.json` too, so published data comes only from production runs. `eval-log.txt` is dev-only and must not reach main.

Flags must be written out statically in `MENU_FLAGS`; Vite substitutes `import.meta.env.VITE_*` at build time, so a computed key silently yields `undefined`.

Verify a flag by clicking through the built site, not by grepping the bundle — page titles are compiled in either way; the flag only governs whether the menu renders them.

### Instagram

`.github/workflows/instagram.yml`, Fridays 17:00 UTC. Modes: `verify`, `dry`, `zkouska` (everything except the final publish), `post`, plus `adhoc` and `reel` for approved one-off content. Instagram fetches the media from a public URL itself, so build and publish are separate steps with a commit in between; files land in `ig-archive/` (outside `public/`, committed with `[skip ci]`) and are published from `raw.githubusercontent.com`. Images must be JPEG. `zkouska` exists because publishing is the one irreversible step — use it rather than testing by posting.

Three producers, one publisher: `post.js` (weekly, from site data, unattended), `adhoc.js` (carousel from an `ig-posts/*.json` spec) and `reel.js` (9:16 video from the same folder, distinguished by `"typ": "reel"`). Only `scripts/lib/instagram.js` calls `media_publish`, so the duplicate-post guard and the wait after `FINISHED` cannot be bypassed. Spec validation lives in `scripts/lib/zadani.js` because the hourly scheduler in `adhoc.js --rezim naplanovane` handles both kinds and must not carry its own copy of the rules.

**Approved content is published byte-for-byte, never re-rendered.** The runner has DejaVu where Windows has Segoe UI, so re-drawing on CI would rewrap text the owner already signed off on. Corollary: do not rebuild an already-published archive locally — it produces a spurious diff against what actually went out.

**Formats follow Instagram's 2026 defaults.** Posts and carousels are 1080×1440 (3:4), not the old 1080×1080 square — `SIRKA`/`VYSKA` in `lib/instagram.js`. Every slide in one carousel must share the ratio; Instagram rejects a mixed set. Rows inside a slide are `flex:none` with the container centring them, because at 3:4 a `flex:1` row stretches across half the canvas when there are only two of them.

Reels: each scene is one Chrome screenshot at 1080×1920 and ffmpeg supplies the motion (`zoompan` over a 2× supersample, `xfade` between scenes). The safe zone is **285 px top, 510 px bottom** and the arithmetic behind it is worth keeping straight, because three constraints stack: Instagram's own UI (no-go 220 top / 450 bottom), the 3:4 window it crops for the profile grid (leaving 240–1440 whichever way that window is aligned), and then the zoom, which magnifies distance from centre by up to 6% and pushes anything sitting on the boundary past it — measured at 212/1457 before this was compensated. Hence 960 − 720/1.06 ≈ 285 and 960 + 480/1.06 ≈ 1412. **Change `ZOOM` in `reel.js` and these numbers must be recomputed.** Sides stay at 90 px though the official minimum is 35. The tricolour sits next to the logo rather than bleeding to the edge, where the zoom would crop it. Video needs `in_range=full:out_range=tv` and `-color_range tv`, otherwise it is tagged `yuvj420p` and looks blown out. Instagram takes minutes to transcode a reel, hence the ten-minute container wait. A reel published through the API cannot carry catalogue music — that is app-only.

Reel audio is two layers, both generated: narration — ElevenLabs when `ELEVENLABS_API_KEY` is set (in `.env.local`, never `.env`, which is committed), otherwise the Windows OneCore voice (`lib/hlas.js` → `hlas.ps1`) — and a music bed picked from the four Eleven Music tracks in `scripts/nastaveni/hudba/` (`lib/hudba.js` still synthesises a sine-wave loop, but only as a fallback for an empty folder), ducked under the speech by `sidechaincompress` and mastered to −14 LUFS. The bed is loudness-normalised to a fixed −26 LUFS rather than given a fixed gain, because the four tracks differ by 11 dB between themselves and a user-supplied MP3 could differ by far more. Generated speech is cached by hash of text+voice+settings in `ig-archive/hlas-cache/` (gitignored): that caps the credit cost of iterating, and it means a rebuilt reel sounds identical to the approved one, which a fresh API call would not. Four things here are easy to get wrong. The system Czech voice is WinRT-only (System.Speech sees just the English Zira, and re-registering the voice would mean editing the registry), so without an ElevenLabs key a reel can only be built on Windows — fine, since the runner never encodes, only publishes. `sidechaincompress` ends with the *shorter* of its two inputs, so the narration mix must be `apad`ded to the full length or the music stops at the last word. **Scene length is derived from the narration**, with `trvani` only a floor, so the finished reel runs longer than the sum of `trvani` in the spec. And ElevenLabs' *stock* voices are recorded by English speakers and carry the accent into Czech — take voices from `GET /v1/shared-voices?language=cs` instead, whose ids work directly in a TTS call without being added to the account first.

Two ElevenLabs quirks worth knowing before debugging anything: the credit counter on `/v1/user/subscription` lags a minute or two behind, so a reading taken right after a build understates the spend; and music costs about 12.5 credits per second (a 40 s bed is ~500) against ~150 credits for a whole reel's narration, which is why beds are generated once and reused rather than per reel. Music licensing differs from speech: commercial use including social video is fine from Starter up, but distribution to music streaming services and to TV/radio is not.

## Gotchas

- Czech quotes in JS strings: `„…"` needs the curly closing quote `"` (U+201C). A straight `"` terminates the string literal and the build error points somewhere unhelpful.
- Never move image bytes through the conversation. A base64 round-trip silently truncated once and produced a corrupt PNG that still had a valid header and correct dimensions. Generate on disk.
- `git pull --rebase` on a branch with a merge commit will flatten it and can drop changes folded into that commit. Use plain `git pull`.
